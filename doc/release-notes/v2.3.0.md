## DOMECS v2.3.0

All seven `@domecs/*` packages at 2.3.0. An additive minor: the second half of the behaviour language for data-defined sims (event-triggered rules and rule effects, contact events), authoring ergonomics (`runSystems` / `render`, transient resources, bridge reset options) and scenes. `^2.0.0` peer ranges still resolve. Specification: [`doc/harness/2026-10-18-harness-engine-gaps.md`](../harness/2026-10-18-harness-engine-gaps.md) §6, §7.3 and §8.

### Highlights

- **Rules take commands.** A rule with `schedule: 'event'` and `on: 'Move'` runs when that event is delivered, so `world.action()` / `bridge.act()` can drive a data-only project. `self: 'event.target'` runs it for one entity (dead or unmatched: nothing happens); without `self` it broadcasts over `query`, or runs once in world scope with an empty `query`. `event.f` reads a payload field, and `other: 'event.b'` binds a second entity (`other.C.f`, `other.id`, `distanceTo(other)`). Event rules resolve `on` through `world.lookupEvent` by default, so `register` the event first.
- **Rules change structure.** `RuleDef.effects` adds `emit`, `spawn` (from `installRules(..., { prefabs })`, with `at` and `set`), `despawn`, `add` and `remove`. Effects are queued only when the entity's actions succeeded and apply at the end of the rule's run, in a fixed order; an `emit` arrives next tick, so chains of event rules are deterministic and a fork taken with `snapshot({ pendingEvents: true })` between the emit and its delivery delivers it too.
- **Contacts.** `installContacts({ position, radius, pairs })` in `@domecs/scene` finds overlapping tagged colliders each step (fixed or per-entity radius, a spatial grid, results independent of cell size) and emits `Contact { a, b, phase: 'begin' | 'end' | 'stay' }` with a declared schema, for `on: 'Contact'` event rules: pickups, damage on contact and goals become rules. The overlapping pairs live in the snapshotted `ContactState` resource, so a restored world continues `begin`/`end` exactly where the source left off. It runs at priority 150, after transform composition at 100.
- **Scenes.** `instantiateScene(world, { name, entities: [{ key, components, parent? }] }, { resolve, refFields })` spawns a level from plain data in array order, links parents by key and turns key references (`refFields`) into live ids. It never throws for bad scene data: unknown components, duplicate keys, missing parents, cycles and unknown references come back as `problems` with paths. Every spawned entity carries `SceneMember { scene, key }`; `unloadScene(world, name)` despawns the scene's trees and `sceneEntities(world, name)` lists its members. "Goto level" is an event rule that records the requested scene; the host swaps scenes after the step.
- **Prime and repaint without a tick.** `world.runSystems(names)` runs named `tick`/`fixed` systems once (for example `composeTransforms` after a restore) without advancing time or firing `tickStart`/`tickEnd`, and reports `{ ran, skipped }`. `world.render()` calls plugin `onRender` only. Neither changes the hash unless a system writes.
- **Transient resources.** `defineResource(name, { default, transient: true })` keeps a camera or HUD cache out of snapshots, saves and both hashes; `restore()` keeps the live value. `describe().resources` reports `transient`.
- **Episode hygiene.** `bridge.reset({ scale, input: 'empty' })` restores the baseline and re-applies the scale and an empty input, which the snapshot does not carry, so an episode that ended paused or with a key held does not leak into the next.
- **Text forks match live worlds.** An entity now lists its components by name, whatever order they were added in. Before, a world restored from `canonicalJson` text and the live world recorded a later despawn's change marks in different orders, so their strict hashes could differ while an `OnRemoved` reader had not run (found by the 2.3 fork-equivalence suite).
- **The fork-equivalence suite and golden cover 2.3.** A live world edited mid-run, with effects, contacts on composed positions and host scene swaps, is matched after every tick by a fresh build restored from its snapshot, and by twelve forks taken with contacts and rule emits in flight (half of them through `canonicalJson` text) with scene swaps between them. The dual-runtime golden adds `rules-event-chain`: event rules and effects forked at step 500 with eleven events in flight; its output is identical under Node and Electron 44.9.0 run as node.

### Behavior changes

- **Component order within an entity is by name.** `world.archetype(entity)`, the order of `componentRemoved` signals and of a despawn's removal marks, and the key order of `snapshot().entities[i].components` follow component names (UTF-16 code-unit order), no longer the order in which an archetype's first entity gained its components. The default `hashSnapshot` is unchanged (it was already canonical). The **strict** hash (`includeChanges: true`, which act-log `baseHash`/checkpoints and fork checks use) can differ from 2.1 and 2.2 for the same run: after a despawn of an entity whose components were added out of name order, while an `OnRemoved` reader has not yet run, 2.3 lists the pending removal marks in name order. So a strict hash or act-log checkpoint recorded by 2.1 or 2.2 is not guaranteed to verify under 2.3 (determinism is per build, which is why hosts stamp `BUILD_ID`); re-record it. `JSON.stringify(snapshot())` text can list components in another order than 2.2 did. Code that relied on insertion order from `archetype()` should sort by its own key.
- **`restore()` empties the delivered-event view.** After a successful restore, `world.events` and the view `runSystems` hands its systems are empty until the next flush. Before, they still held what the abandoned timeline delivered at its last tick, so a world restored in place and a fresh world restored from the same snapshot could run a system on different events.
- **`event.f` and `other` parse.** They were "reserved word" parse errors. Outside an event rule (and in `compileWorldExpression`) they are compile errors at the same position, so such a rule is still rejected; only the message changes.
- **`ResourceDescriptor` gains `transient`** (`describeResource`, `describe().resources`). Code that compares descriptors with an exact shape needs the new field.

Snapshots are unchanged: still format v3, with no new fields. A transient resource is simply absent from 2.3 snapshots; when a 2.3 world restores an older save that holds a value for a resource it has registered as transient, that value is ignored. The 2.1 and 2.2 golden fixtures and their hashes are byte-identical in 2.3.

### Type-level changes

- **`RuleDefPath` widens** with `'on'`, `'self'`, `'other'` and `{ effect: number; part: string }`. Keep a default branch when you switch on it, as the 2.1 and 2.2 notes said.
- `RuleDef.schedule` gains `'event'`, and `RuleDef` gains `on`, `self`, `other` and `effects`.
- `AstNode` gains `event` (`event.f`) and `other` nodes.
- `EvalEnv.self` accepts `undefined`, and `EvalEnv` gains optional `eventField` and `other` hooks.
- `ResourceOptions` gains `transient`; `ResourceDescriptor` gains `transient`.
- `World` gains `runSystems` and `render`; `AgentBridge.reset` takes optional `AgentResetOptions`.

Code that does not switch exhaustively over these unions, or implement `World` itself, compiles unchanged.

### New APIs

- `@domecs/core`:
  - `World.runSystems(names)`, `World.render()`;
  - `defineResource(name, { transient: true })`;
  - `AgentBridge.reset(options?)` and the type `AgentResetOptions`.
- `@domecs/rules`:
  - event rules: `RuleDef.schedule: 'event'`, `on`, `self`, `other`; `InstallRulesOptions.resolveEvent` (also a `compileRule` option);
  - effects: `RuleDef.effects`, the type `RuleEffectDef`, `InstallRulesOptions.prefabs` (also a `compileRule` option);
  - `walkFieldRefs` is now exported from the package entry (it shipped only in `dist/ast.js` in 2.2).
- `@domecs/scene`:
  - contacts: `installContacts`, `Contact`, `ContactState`, and the types `ContactsOptions`, `ContactPayload`, `ContactPhase`, `ContactStateValue`;
  - scenes: `instantiateScene`, `unloadScene`, `sceneEntities`, `SceneMember`, and the types `SceneData`, `SceneEntityData`, `SceneProblem`, `InstantiateSceneOptions`, `InstantiateSceneResult`.

The full signatures are in [`doc/api-surface/`](../api-surface/) and [`doc/api.md`](../api.md). `doc/api.md` has a runnable doctest for each new API (`rules-event-effects`, `scene-contacts`, `scene-goto-level`, `run-systems-render`, `transient-resources`, `agent-reset-options`).

### Upgrading from 2.2.0

1. Upgrade all `@domecs/*` packages to 2.3.0 together. The packages' `@domecs/core` peer range is now `^2.3.0`.
2. Add a default branch to any exhaustive `switch` over `RuleDefPath`, `AstNode['kind']` or `RuleDef['schedule']`.
3. If code read `world.archetype(entity)` or a snapshot's component keys expecting add order, sort by your own key. Compare snapshots with `hashSnapshot`, never `JSON.stringify`.
4. Optional, for data-driven projects and agents:
   - Declare commands with a `schema`, `world.register` them, and handle them with event rules; use `effects` instead of host systems for spawning, despawning and tagging.
   - Replace hand-written overlap systems with `installContacts` and `on: 'Contact'` rules.
   - Load levels with `instantiateScene` and swap them from the host after an event rule records the request.
   - Mark camera and HUD resources `transient: true`, and call `bridge.reset({ scale: 1, input: 'empty' })` at episode boundaries.
   - Goldens and default hashes recorded on 2.1 and 2.2 stay valid. Strict hashes (and act-log checkpoints) recorded on 2.1 or 2.2 stay valid unless a despawn left removal marks unread (see "Behavior changes"); re-record those on 2.3.
